# AGENTS.md — AI_VTUBER

Цей файл — інструкція для AI-агентів (Claude Code, Copilot, Cursor тощо), які працюють з цим репозиторієм. Мета: не ламати те, що вже налагоджено ціною багатьох ітерацій, і не наступати на вже відомі граблі.

## Що це за проєкт

Локальний голосовий асистент/AI VTuber "Селті" — повністю офлайн, без GPU. Конвеєр: мікрофон → VAD-запис → Whisper (STT) → Gemma GGUF через llama.cpp (LLM) → StyleTTS2 UA (TTS) → колонки. Працює на слабкому CPU (Intel i5-8265U, 4 фізичних ядра/8 потоків, 12 ГБ RAM, з яких ~4 ГБ займає Windows).

**Головний, постійний обмежувач у цьому проєкті — не якість коду, а бюджет заліза.** Будь-яка зміна, яка додає модель, потік чи залежність, має бути оцінена насамперед через призму RAM і CPU, а вже потім — елегантності коду.

## Архітектура (поточна, не плутати зі старою)

У репозиторії існували дві різні концепції пайплайну, і вони одного разу вже перемішались через невдалий git-merge:

1. **Стара (потокова, з `queue.Queue`)** — три постійні daemon-потоки (STT/LLM/TTS), команда "СТОП" голосом для переривання посеред мовлення, `STOP_WORDS`.
2. **Поточна (послідовна)** — `main.py` має простий цикл `while True`: записати → розпізнати → згенерувати відповідь → озвучити → дочекатись завершення → повторити. TTS усередині себе має два допоміжні потоки (`_text_processing_worker`, `_audio_playback_worker`), але сам головний цикл — послідовний, без команди "стоп" голосом під час мовлення.

**Якщо не сказано інше — проєкт зараз живе в другій, послідовній архітектурі.** Не повертай першу без явного прохання користувача. Якщо бачиш код обох одночасно в одному файлі (дубльовані функції, `STOP_WORDS`, `stop_event`/`interrupt_event` поруч із простим `while True` без черг) — це ознака незавершеного мерджу, а не навмисний дизайн. Дивись розділ "Відомі граблі" нижче.

## Бюджет потоків CPU — не чіпай без вимірювання

Це найкрихкіша частина проєкту. Дефолти в `config.json`, до яких дійшли експериментально:

```json
"llm": { "n_threads": 1, "n_threads_batch": 4 },
"tts": { "n_threads": 3 }
```

Причина саме такого розподілу (1+3=4, увесь бюджет фізичних ядер):
- `llm.n_threads_batch` — потоки для **prefill** (обробка промпту). Тут можна брати максимум (4), бо TTS у цей момент ще нічого не робить.
- `llm.n_threads` — потоки для **decode** (генерація токенів). У послідовній архітектурі LLM здебільшого встигає закінчити генерацію ще до того, як TTS почне рендерити перше речення, тому це число можна тримати малим.
- `tts.n_threads` — StyleTTS2 рендерить довше за LLM-генерацію (фіксований оверхед ~3.5-4s на виклик незалежно від довжини), тому саме йому варто віддавати основний бюджет ядер.

**Правило:** `llm.n_threads + tts.n_threads` не повинно суттєво перевищувати 4 (кількість фізичних ядер). Гіперпотоки (8 логічних) майже не дають приросту для важких матричних обчислень — не вважай їх додатковим бюджетом.

**Перед зміною цих чисел — обов'язково прожени однаковий тест до і після** (наприклад: "привіт" → коротка репліка → довша репліка) і порівняй час у логах `[StyleTTS2] Шматок ... готовий за Xs`. Не покладайся на інтуїцію — контенція за ядра на цьому залізі непередбачувана без вимірювання.

**`torch.set_num_threads()` для TTS має викликатись ДО створення `StyleTTS2(...)`**, інакше PyTorch за замовчуванням хапає всі доступні ядра.

## TTS-рушії: PyTorch vs ONNX (`tts.engine`)

`tts_handler.py` підтримує два рушії синтезу, перемикання — полем `tts.engine` в `config.json`:

- **`"pytorch"`** (дефолт) — повна модель `StyleTTS2`. Єдиний рушій, що підтримує `tts.mode=2` (динамічне клонування голосу з `.wav` через `extract_voice_features`), бо ONNX-граф не містить voice-encoder'а.
- **`"onnx"`** — `onnxruntime.InferenceSession` над `models/styletts2.onnx`. Підтримує лише `tts.mode=1` (готовий `.pt`-пресет); при `mode=2` + `engine=onnx` `TTSHandler._prepare_voice()` навмисно кидає `ValueError` при старті — це задумана поведінка, не баг, не "полагодь" це тихим фолбеком на pytorch.

**Виміряно на цьому залізі** (i5-8265U, 4 ядра, `tts.n_threads=3`, той самий пресет, ідентичні репліки, `btop` під час старту):

| | PyTorch | ONNX | Різниця |
|---|---|---|---|
| Синтез шматка ~33 симв. | 3.98s | 3.02s | ~24% швидше |
| Синтез шматка ~68 симв. | 6.08s | 4.23s | ~30% швидше |
| RAM у стані спокою (`Mem`, `btop`) | 10.5G/11.8G | 9.43G/11.8G | ~1 ГБ менше |

Тобто ONNX виграє і швидкість, і RAM одночасно — на цьому залізі RAM впритул до ліміту (89% зайнято на PyTorch у стані спокою, до жодного важкого запиту), тож економія ONNX — не косметика, а реальний запас проти свопінгу.

**Workflow для клонованого голосу + швидкого ONNX:** клонування виноситься в окремий одноразовий крок через `extract_preset.py` (повна PyTorch-модель вантажиться лише на час скрипта), результат — звичайний `.pt` у `voices/`, який далі використовується як `tts.preset_filename` з `tts.mode="1"` і `tts.engine="onnx"`. Так реальний пайплайн ніколи не тримає в пам'яті повну модель заради клонування.

**Якщо додаєш зміну в `_synthesize`/`_clone_style`/`_add_style_noise`** — пам'ятай, що це єдина точка розходження між рушіями: `pytorch`-гілка працює з `torch.Tensor`, `onnx`-гілка — з `np.ndarray`. Не додавай логіку синтезу деінде в `_text_processing_worker`, інакше розсинхрон між рушіями повернеться.

## Пам'ять — постійно тісний бюджет

12 ГБ - 4 ГБ Windows = ~8 ГБ доступно. Реальний баланс перевіряй через Диспетчер завдань (`Committed` не повинен перевищувати фізичну RAM — інакше йде свопінг на диск, і CPU буде простоювати на I/O, а не рахувати).

Відомі споживачі:
- Gemma E4B Q4_K_M ≈ 3-4.5 ГБ (E2B — суттєво легша, але дає гірше дотримання мови, див. нижче)
- Whisper small int8 ≈ 250-400 МБ
- StyleTTS2 UA (`tts.engine="pytorch"`) ≈ 700 МБ-1 ГБ
- StyleTTS2 UA (`tts.engine="onnx"`) — виміряно ~1 ГБ менше за pytorch-рушій (немає повної моделі з енкодером/декодером, лише ORT-сесія + токенайзер)
- **mBART verbalizer** (якщо `use_verbalizer: true`) ≈ 1.2-2.4 ГБ — **тримай вимкненим** (`false`). `num2words` в `llm_handler.py`/`tts_handler.py` покриває практично всі побутові числа без цієї важкої моделі.

Перед тим як додавати нову модель (embedding для пам'яті, детектор мови тощо) — заміряй її RSS окремо, а не покладайся на документацію моделі.

## Відомі граблі (не наступай повторно)

1. **`re.search()` для пошуку "першого достатньо довгого речення" в `generate_response`** — якщо шукати найпростішим `re.search`, він завжди повертає найперший збіг пунктуації і "застряє", якщо те речення коротше за поріг. Треба перебирати `re.finditer` і брати перший, що задовольняє довжину. Цей баг уже був і виправлений — не спрощуй код назад до `re.search`.

2. **Подвійна нарізка тексту.** LLM (`llm_handler.py`) і TTS (`tts_handler.py`) обидва мають логіку нарізки на шматки. Якщо LLM віддає короткі шматки, а TTS ще й ріже їх додатково — кожен шматок платить фіксований оверхед виклику StyleTTS2 (~4s) окремо, і сумарний час вибухає. Якщо змінюєш пороги нарізки в одному файлі — перевір узгодженість з іншим.

3. **Кодування mp3 всередині гарячої фази.** Ніколи не роби `AudioSegment.from_mp3()` + конкатенація + `export()` на кожному шматку тексту під час активного TTS-рендеру — це ffmpeg-декодування/кодування прямо в момент максимального навантаження CPU, і воно даватиме хаотичні стрибки часу синтезу (спостережено: однаковий текст 4.27s або 8.48s залежно від того, чи йшов паралельно re-export). Накопичуй сирі wav-чанки в `_session_wavs` і кодуй **один раз** у `flush_session_audio()` після того, як репліка повністю відзвучала.

4. **`KMP_DUPLICATE_LIB_OK=TRUE`** на початку `main.py` — це маскування конфлікту версій OpenMP-рантайму, а не лікування. Якщо з'являється нестабільність/Access Violation під навантаженням кількох потоків — підозрюй цей прапорець, а не одразу йди балансувати `n_threads`.

5. **Незавершені git-merge конфлікти.** У цього репозиторію вже була ситуація, коли `git add` виконали на файл, де фізично лишились маркери `<<<<<<< / ======= / >>>>>>>`, і git вважав конфлікт "вирішеним", хоча файл був синтаксично непридатний. **Перед будь-яким комітом після merge/rebase:**
   ```powershell
   Select-String -Path *.py -Pattern "^<<<<<<<|^=======|^>>>>>>>"
   python -m py_compile main.py llm_handler.py tts_handler.py audio_handler.py
   ```
   Обидві команди мають повернути порожній вивід/без помилок.

6. **`n_threads` без `n_threads_batch` у `Llama(...)`.** Якщо хтось (людина чи агент) прибере `n_threads_batch` з виклику конструктора — prefill почне ділити той самий малий бюджет потоків, що й decode, і "Пошук думки" в логах різко зросте (спостережено: 8.29s замість 1.5-2.5s).

7. **Змішування мов при слабшій LLM.** Менші квантування/моделі (наприклад Gemma E2B замість E4B) частіше вставляють російські слова в україномовну відповідь ("отлично", "это", "теперь"), особливо в саркастичному тоні. Це критично, бо `_clean_text_for_tts` **не фільтрує мову**, і такий текст летить прямо в StyleTTS2 UA, навчену лише на українській фонетиці — вимова буде зламана. Якщо змінюєш модель на легшу — обов'язково перевір кілька реплік на предмет мовного змішування, перш ніж вважати заміну успішною.

8. **Whisper-галюцинації на короткому/нечіткому старті запису.** Спостережено кілька разів: "Привіт" → "Дивіт", "Цікавим" → "Мисикавим", "Розкажи" → "Проскажі". `hallucination_blacklist` у `audio_handler.py` ловить лише повністю вигадані фрази-привиди (типу "дякую за перегляд"), а не спотворення реальних слів. Якщо це стає проблемою — дивись у бік точнішого `initial_prompt` або нижчого `silence_duration` перед стартом запису (менше "холостого" аудіо на вході).

9. **`tts.mode=2` (клонування голосу) з `tts.engine=onnx` — навмисна помилка, не баг.** `_prepare_voice()` кидає `ValueError` одразу при старті, якщо хтось виставить цю комбінацію. Причина не в недбалості, а в тому, що `models/styletts2.onnx` експортований без voice-encoder'а — граф фізично не вміє рахувати `extract_voice_features`. Не "фіксь" це підміною на мовчазний fallback у `pytorch`: користувач мав намір отримати ONNX-швидкість, а тиха підміна рушія — це прихована деградація продуктивності без пояснення. Якщо потрібен і клонований голос, і ONNX-швидкість — правильний шлях: `extract_preset.py` (клонування офлайн, один раз) → `.pt`-пресет → `mode=1` + `engine=onnx`.

## Незавершені експерименти / відкриті питання

- **`diffusion_steps`** у `tts_handler.py` (`self.multi_model.model.diffusion_steps` і паралельно `self.multi_model.model.args.diffusion_steps`) — теоретично мало б лінійно впливати на швидкість синтезу StyleTTS2, але останній тест (steps=3→1) **не показав очікуваного прискорення**, а подекуди навіть сповільнення. Перед тим як покладатись на цей параметр — перевір `Select-String -Path tts_handler.py -Pattern "diffusion_steps"`, що зміна дійсно застосована в обох місцях, і повтори вимір без відкритого Диспетчера завдань (сам моніторинг забирає CPU-час на цьому залізі й спотворює замір). Це стосується лише `engine="pytorch"` — в ONNX-графі кроки дифузії зашиті на етапі експорту, з коду їх не поміняти.
- ~~ONNX-варіанти моделі — не досліджені~~ — **завершено.** `tts.engine="onnx"` дає ~25-30% приросту швидкості синтезу і ~1 ГБ економії RAM (виміряно, цифри в розділі "TTS-рушії" вище). Обмеження: без клонування голосу наживо (`mode=2`), тільки готові пресети (`mode=1`) — workflow для клонованого голосу на ONNX є, через `extract_preset.py`.
- Динамічне перемикання `torch.set_num_threads()` між фазами (менше під час LLM-генерації, більше після) обговорювалось, але не реалізовано — поточний статичний розподіл 1+3 вже дав суттєвий приріст і поки що достатній.
- **Розпаралелення головного циклу між STT/LLM/TTS.** Користувач відкритий до цього в майбутньому (розподілити роботу між 4 фізичними ядрами), але це **не поточний пріоритет і не роби це без явного прохання**. Причина обережності конкретна, не загальна: у цьому репозиторії вже була стара, чергова архітектура з трьома постійними потоками (розділ "Архітектура" вище), і повернення до неї частковими правками — це саме той сценарій незавершеного мерджу, який уже раз ламав файли (див. "Відомі граблі" п.5). Якщо колись братимешся за це — став умисно, як нову версію архітектури цілком, а не як патч поверх послідовного циклу.

## Перевірка перед комітом

Мінімальний чек-лист для будь-якої зміни в `*.py` чи `config.json`:

```powershell
python -m py_compile main.py llm_handler.py tts_handler.py audio_handler.py extract_preset.py
python .\main.py
```

Якщо зміна стосувалась `tts_handler.py` — прожени `main.py` **з обома значеннями `tts.engine`** ("pytorch" і "onnx"), а не лише з тим, яке зараз стоїть у `config.json`. Це найлегше зламати незавершеним рефакторингом: одна гілка компілюється, друга падає в рантаймі лише коли `self.engine` дорівнює конкретному значенню.

Скажи щось голосом, дочекайся 2-3 реплік, переконайся що:
- нема necropsy-виведення в консоль (винятки, traceback)
- `output.mp3` записується один раз наприкінці репліки (`💾 Монолог збережено`), а не по кожному шматку
- перше речення озвучується окремо й швидко, а не разом з усім монологом

Порівняй час у логах `[StyleTTS2] Шматок ... готовий за Xs` з попереднім заміром перед зміною — регресія швидкості на 20%+ без пояснення означає, що щось зламано (найчастіше — конкуренція за потоки чи свопінг пам'яті).

## Стиль коду в цьому проєкті

- Логування — через `from logger_config import log` (`log.info/warning/error/critical`), не голий `print()` у нових модулях (винятки — `main.py` під час запуску/прогріву, де це історично лишилось; не обов'язково рефакторити заради цього, але не додавай нового `print()`).
- Українські коментарі й лог-повідомлення з емодзі-префіксами (🎙️🧠📥✅❌🔥💾) — усталений стиль проєкту, дотримуйся його в нових повідомленнях для консистентності виводу.
- Конфігурація — все, що може мінятись між запусками (пороги, промт, потоки), йде в `config.json`, а не хардкодиться в коді. Якщо додаєш новий параметр — додай `.get('key', default)` з розумним дефолтом, щоб старі `config.json` не ламались.
