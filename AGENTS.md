# AGENTS.md — AI_VTUBER

Цей файл — інструкція для AI-агентів (Claude Code, Copilot, Cursor тощо), які працюють з цим репозиторієм. Мета: не ламати те, що вже налагоджено ціною багатьох ітерацій, і не наступати на вже відомі граблі.

## Що це за проєкт

Локальний голосовий асистент/AI VTuber "Селті" — повністю офлайн, без GPU. Конвеєр: мікрофон → VAD-запис → Whisper (STT) → Gemma GGUF через llama.cpp (LLM, опційно з LoRA-адаптером) → StyleTTS2 UA (TTS) → колонки. Працює на слабкому CPU (Intel i5-8265U, 4 фізичних ядра/8 потоків, 12 ГБ RAM, з яких ~4 ГБ займає Windows).

**Головний, постійний обмежувач у цьому проєкті — не якість коду, а бюджет заліза.** Будь-яка зміна, яка додає модель, потік чи залежність, має бути оцінена насамперед через призму RAM і CPU, а вже потім — елегантності коду.

## Архітектура (поточна, не плутати зі старою)

У репозиторії існували дві різні концепції пайплайну, і вони одного разу вже перемішались через невдалий git-merge:

1. **Стара (потокова, з `queue.Queue`)** — три постійні daemon-потоки (STT/LLM/TTS), команда "СТОП" голосом для переривання посеред мовлення, `STOP_WORDS`.
2. **Поточна (послідовна)** — `main.py` має простий цикл `while True`: записати → розпізнати → згенерувати відповідь → озвучити → дочекатись завершення → повторити. TTS усередині себе має два допоміжні потоки (`_text_processing_worker`, `_audio_playback_worker`), але сам головний цикл — послідовний, без команди "стоп" голосом під час мовлення.

**Якщо не сказано інше — проєкт зараз живе в другій, послідовній архітектурі.** Не повертай першу без явного прохання користувача. Якщо бачиш код обох одночасно в одному файлі (дубльовані функції, `STOP_WORDS`, `stop_event`/`interrupt_event` поруч із простим `while True` без черг) — це ознака незавершеного мерджу, а не навмисний дизайн. Дивись розділ "Відомі граблі" нижче.

**Розпаралелення головного циклу між STT/LLM/TTS.** Користувач відкритий до цього в майбутньому, але це **не поточний пріоритет і не роби це без явного прохання**. У репозиторії вже була стара, чергова архітектура з трьома постійними потоками, і повернення до неї частковими правками — це саме той сценарій незавершеного мерджу, який уже раз ламав файли (див. "Відомі граблі" п.5). Якщо колись братимешся за це — став умисно, як нову версію архітектури цілком, а не як патч поверх послідовного циклу.

## Бюджет потоків CPU — вимірюй через `benchmark.py`, не вручну

Це найкрихкіша частина проєкту, і дефолти в `config.json` кілька разів мінялись під тиском **виміряних** даних, а не інтуїції:

```json
"llm": { "n_threads": 2, "n_threads_batch": 4 },
"tts": { "n_threads": 3, "parallel_chunks": 1 }
```

Історія висновків (кожен підтверджено `benchmark.py` із зафіксованим `seed`, не одиничним ручним тестом):
- `llm.n_threads=1` — найгірший варіант з усіх протестованих, стабільно програє `llm.n_threads=2` на 15-25% по сумарному часу репліки.
- `llm.n_threads=3` — трохи краще за `2`, але різниця вже в межах шуму заміру (~0.1-0.5с на репліку).
- `llm.n_threads=4` **разом з** `tts.n_threads=4` — протестовано, **не дало виграшу** порівняно з `llm=3`. Причина: LLM і TTS — не два повністю послідовні етапи, вони реально перекриваються в часі (поки LLM генерує сегмент N+1, TTS ще озвучує сегмент N у фоновому потоці), тож `4+4=8` логічних потоків одночасно хочуть 4 фізичні ядра — саме той oversubscription, від якого й застерігало початкове правило.
- **Правило лишається чинним:** `llm.n_threads + tts.n_threads` не повинно суттєво перевищувати 4 (фізичні ядра), і це стосується не лише статичної суми в конфізі, а й факту, що обидва модулі можуть реально працювати одночасно навіть у "послідовній" архітектурі головного циклу.

**Перед зміною цих чисел — прожени `python .\benchmark.py`** (додай свій варіант у список `VARIANTS`, якщо його там немає) замість одиничного ручного тесту "до/після". Ручні заміри на цьому проєкті вже кілька разів вводили в оману через шум одного прогону (±10-20% між ідентичними запусками) — тільки кілька повторів із зафіксованим `seed` дають надійний висновок. Деталі — розділ "benchmark.py" нижче.

**`torch.set_num_threads()` для TTS має викликатись ДО створення `StyleTTS2(...)`**, інакше PyTorch за замовчуванням хапає всі доступні ядра.

**`torch.set_num_interop_threads()` можна викликати лише ОДИН РАЗ за весь час життя процесу**, незалежно від значення — повторний виклик кидає `RuntimeError`, навіть з тим самим числом. У `main.py` це ніколи не спрацьовує (один `TTSHandler` на весь процес), але в `benchmark.py`, де на кожен варіант конфігурації створюється новий `TTSHandler` в одному й тому ж процесі — це реальна пастка. `tts_handler.py` вже огортає цей виклик у `try/except RuntimeError: pass` — не прибирай цей try/except, вважаючи його зайвим, він рятує саме цей сценарій.

## TTS-рушії: PyTorch vs ONNX (`tts.engine`)

`tts_handler.py` підтримує два рушії синтезу, перемикання — полем `tts.engine` в `config.json`:

- **`"pytorch"`** — повна модель `StyleTTS2`. Єдиний рушій, що підтримує `tts.mode=2` (динамічне клонування голосу з `.wav` через `extract_voice_features`), бо ONNX-граф не містить voice-encoder'а.
- **`"onnx"`** — `onnxruntime.InferenceSession` над `models/styletts2.onnx`. Підтримує лише `tts.mode=1` (готовий `.pt`-пресет); при `mode=2` + `engine=onnx` `TTSHandler._prepare_voice()` навмисно кидає `ValueError` при старті — це задумана поведінка, не баг, не "полагодь" це тихим фолбеком на pytorch.

**Виміряно на цьому залізі** (i5-8265U, 4 ядра, `tts.n_threads=3`, той самий пресет, ідентичні репліки):

| | PyTorch | ONNX | Різниця |
|---|---|---|---|
| Синтез шматка ~33 симв. | 3.98s | 3.02s | ~24% швидше |
| Синтез шматка ~68 симв. | 6.08s | 4.23s | ~30% швидше |
| RAM у стані спокою | 10.5G/11.8G | 9.43G/11.8G | ~1 ГБ менше |
| Сумарний час репліки (`benchmark.py`, `llm=2/tts=3` для обох) | 22.35s | 20.41s | ~9% швидше |

ONNX виграє за швидкістю й пам'яттю, **але користувач суб'єктивно вважає, що PyTorch звучить приємніше** на слух — це не вимірювалось об'єктивно (не можемо перевірити внутрішні параметри готового `styletts2.onnx`, зокрема кількість кроків дифузії — вони зашиті в граф на етапі експорту кимось іншим, з коду їх не поглянути й не змінити). Не вважай ONNX однозначно "кращим рушієм за замовчуванням" — коли `tts.mode=1` (не потрібне клонування), вибір рушія лишається **на розсуд користувача**, це компроміс швидкість/пам'ять проти суб'єктивної якості голосу, а не технічне питання з єдиною правильною відповіддю.

**Workflow для клонованого голосу + швидкого ONNX:** клонування виноситься в окремий одноразовий крок через `extract_preset.py` (повна PyTorch-модель вантажиться лише на час скрипта), результат — звичайний `.pt` у `voices/`, який далі використовується як `tts.preset_filename` з `tts.mode="1"` і `tts.engine="onnx"`.

**Якщо додаєш зміну в `_synthesize`/`_clone_style`/`_add_style_noise`** — пам'ятай, що це єдина точка розходження між рушіями: `pytorch`-гілка працює з `torch.Tensor`, `onnx`-гілка — з `np.ndarray`. Не додавай логіку синтезу деінде в `_text_processing_worker`, інакше розсинхрон між рушіями повернеться.

## `parallel_chunks` — ЛАМАЄ ЗВУК, не вмикай без верифікації потокобезпеки

`tts.parallel_chunks` (дефолт `1`) керує тим, скільки шматків тексту `TTSHandler` синтезує одночасно через `ThreadPoolExecutor`. **Значення > 1 підтверджено спричиняє чутне пошкодження звуку** — заїкання на початку окремих слів ("Ти" → "Т ииии", "Просто" → "Пр росто"), спостережено на **обох** рушіях (не лише pytorch, де конкурентна безпека forward-виклику й так під питанням, а й onnx, де сам `Run()` документовано безпечний для конкурентних викликів).

Причина, найімовірніше, не в `onnxruntime.Run()`/`torch forward`, а в препроцесингу ДО них — `Stressifier()` (ukrainian_word_stress), `ipa_uk.ipa()`, `self.tokenizer.encode()` (StyleTTS2Tokenizer). Жодна з цих зовнішніх бібліотек не документує потокобезпеку; судячи з локалізації пошкодження (завжди на самому початку слова), десь усередині є спільний мутабельний стан (кеш/буфер), який ловить гонку даних саме в момент старту обробки нового слова.

**Не вмикай `parallel_chunks > 1`** без явного підтвердження, що ці три виклики дійсно потокобезпечні (наприклад, окремий екземпляр `Stressifier`/токенайзера на кожен потік пулу замість одного спільного на весь `TTSHandler`). Це стосується й швидкості теж, не лише коректності: через спільний, фіксований пул потоків рушія (`tts.n_threads`) кілька одночасних синтезів не отримують "більше ядер" — вони ділять той самий бюджет, лише з додатковим оверхедом синхронізації. Заміри з `parallel_chunks=2` показували і виграш, і програш залежно від того, наскільки випадково синтез одного шматка встигав "сховатись" за час відтворення попереднього — це ненадійний, нестабільний ефект, і корисність такого виграшу нульова, поки лишається баг з пошкодженням звуку.

## LoRA-адаптери (`llm.lora_path` / `llm.use_lora` / `llm.lora_scale`)

`LLMHandler` підтримує опційний LoRA-адаптер поверх базової GGUF-моделі — той самий механізм, що й `--lora` у `llama-cli.exe`. Параметри:

```json
"llm": {
  "model_path": "models/base-model.gguf",
  "lora_path": "models/adapter-lora.gguf",
  "use_lora": true,
  "lora_scale": 1.0
}
```

`use_lora` — перемикач "з LoRA / без", той самий патерн, що й `tts.use_verbalizer`: шлях лишається прописаним завжди, вмикається/вимикається однією зміною `true`/`false`. Якщо `lora_path` вказано, а файл не знайдено — модель вантажиться БЕЗ LoRA з попередженням у лог, не падає.

**Сумісність:** GGUF-формат LoRA-адаптерів (без потреби заздалегідь мержити ваги) підтримується не в усіх версіях `llama-cpp-python` — `requirements.txt` каже лише `>=0.2.50` (стара нижня межа). Якщо `Llama(lora_path=...)` кидає `TypeError: unexpected keyword argument`, треба `pip install --upgrade llama-cpp-python`.

**Персонаж може бути вже "в LoRA".** Якщо LoRA натренована з персонажем (напр. модель відповідає "Я Селті" навіть у голому `llama-cli.exe` без жодного системного промпту) — існуючий `character.system_prompt` може стати зайвим або конфліктувати з уже натренованою поведінкою. Перевіряй на практиці після підключення нової LoRA, не припускай сумісність автоматично.

## Мікрофон: pre-roll і VAD padding (`mic.*`, `stt.vad_*`)

Два незалежні шари захисту від обрізання країв фрази — не плутай їх, вони на різних рівнях:

1. **`main.py` / `record_microphone_clean`** — фізичний рівень запису. Кільцевий буфер (`deque`) тримає останні `mic.pre_roll_ms` (дефолт 350) аудіо ще ДО того, як RMS-гучність перевищить `mic.threshold` — без цього перший склад (м'який приголосний, видих) регулярно ковтається, бо на момент спрацювання порогу він уже пролетів повз і був відкинутий. `mic.silence_duration` — скільки тиші після мовлення чекати перед зупинкою запису (компроміс: занадто мало — обрізає кінець фрази під час природної паузи; занадто багато — довге очікування).
2. **`audio_handler.py` / Whisper VAD** — вже всередині записаного файлу, як Whisper сам ділить його на сегменти мовлення (Silero VAD). `stt.vad_speech_pad_ms` (дефолт 300) — запас з обох боків кожного знайденого сегмента; без нього Silero-VAD часто ріже впритул і губить перший/останній склад **у розпізнаванні**, навіть якщо мікрофон-рівень (пункт 1) записав усе правильно.

Якщо скарга "ковтає початок/кінець фрази" — спершу з'ясуй, на якому рівні проблема (слухай сам `input/temp_voice.wav`: якщо звук цілий, а текст обрізаний — проблема в Whisper VAD, підкручуй `vad_speech_pad_ms`; якщо сам звук уже без початку — проблема в `pre_roll_ms`/`threshold`).

## Логування репліки — друкується ЖИВЦЕМ з `_audio_playback_worker`, не з `main.py`

Історія кількох ітерацій: спершу друк per-chunk йшов одночасно з двох потоків (LLM у `main.py`, TTS у `tts_handler.py`) і переплітався хаотично; потім увесь друк перенесли в один пост-хок прохід після `wait_until_done()` — це дало чистий порядок, але користувач втратив відчуття реального часу (весь текст з'являвся одним блоком вже ПІСЛЯ того, як усе відзвучало). Фінальний варіант: друк живе в `_audio_playback_worker`, точно в момент, коли фраза фізично йде в динаміки — і це єдине джерело живого друку по репліках, `main.py` більше не друкує нічого per-segment.

Механізм передачі даних:
- `main.py` рахує `seg_time` (час LLM на цей сегмент) і передає його прямо в чергу: `tts_module.play_text_async(sentence, llm_time=seg_time)`.
- `_text_processing_worker` приписує `llm_time` ЛИШЕ першому під-шматку сегмента (`i == 1`), якщо сегмент розрізало на кілька TTS-шматків — інакше час LLM рахувався б по кілька разів.
- Кожен `metrics_entry` (dict) іде в `audio_queue` РАЗОМ з аудіо, як кортеж `(audio_chunk, metrics_entry)` — `_audio_playback_worker` дописує в той самий об'єкт `played_at`/`silence_before` і одразу друкує звіт, перш ніж викликати `sd.play()`.

Схема `chunk_metrics`: `{"text", "chars", "synth_time", "llm_time", "combined", "ready_at", "played_at", "silence_before"}`. `silence_log` — список **усіх** виміряних пауз (не лише тих, що друкуються — поріг друку 0.3с, а `benchmark.py` читає повний список без порогу).

**Якщо чіпаєш цю логіку** — не переноси друк назад у `main.py` чи в `_text_processing_worker` без вагомої причини: `_audio_playback_worker` — єдине місце, де момент друку гарантовано збігається з моментом, коли фраза РЕАЛЬНО звучить, а не коли вона щойно синтезувалась (ці моменти можуть відрізнятись на секунди, особливо якщо `audio_queue` вже має накопичені шматки).

## benchmark.py — автотестування конфігурацій

Прогонить одну й ту саму фразу через LLM+TTS з різними конфігураціями (`VARIANTS` — список `(назва, overrides)`), кілька повторів на варіант, виводить порівняльну таблицю + CSV. Мікрофон/STT не бере участі — текст подається напряму.

Ключові деталі дизайну, важливі при редагуванні:
- **`--seed`** (дефолт 42) фіксує семплінг LLM, щоб та сама фраза давала **той самий текст** у кожному повторі/варіанті — без цього порівняння забруднюється випадковістю відповіді LLM, а не лише швидкістю заліза. **Навіть із фіксованим seed текст не буде побітово ідентичним між різними `n_threads`** — floating-point накопичення в llama.cpp злегка залежить від кількості потоків, тож довжини реплік можуть трохи відрізнятись. Це нормально, якщо довжини близькі (у межах кількох символів) — суттєвіша розбіжність означає щось інше зламалось.
- **`TTSHandler.shutdown()` — обов'язковий виклик між варіантами.** `_text_processing_worker`/`_audio_playback_worker` — нескінченні `while True` на bound-методах `self`; поки потік живий, він тримає посилання на весь `TTSHandler` (модель/сесію) навіть після `del`. Без `shutdown()` (який кладе `_STOP_SENTINEL` в обидві черги й `join()`-ить потоки) пам'ять від кожного попереднього варіанта накопичувалась би — це реально спостерігалось: RAM забивалась до 96% ще на третьому (легкому, ONNX) варіанті, задовго до найважчого pytorch. Якщо додаєш новий фоновий потік у `TTSHandler` — обов'язково додай його зупинку в `shutdown()` теж.
- **`pytorch`-варіант навмисно останній у списку `VARIANTS`.** Навіть із робочим `shutdown()`, зайва обережність не завадить — найважчий варіант не повинен впливати на виміри легших, якщо все ж лишиться якийсь незвільнений залишок.
- Після кожного варіанта — явний `del llm_module, tts_module; gc.collect()` у `finally`.
- `--mute` вимикає реальне відтворення (швидше для довгих сесій), але тоді "тиша" вимірюється лише по завершенню синтезу, без урахування реальної тривалості аудіо — для фінальної перевірки найкращого варіанта краще прогнати ще раз БЕЗ `--mute`.

## Пам'ять — постійно тісний бюджет

12 ГБ - 4 ГБ Windows = ~8 ГБ доступно. Реальний баланс перевіряй через Диспетчер завдань/`btop` (`Committed`/`Mem` не повинен перевищувати фізичну RAM — інакше йде свопінг на диск, і CPU буде простоювати на I/O, а не рахувати).

Відомі споживачі:
- Gemma E4B Q4_K_M ≈ 3-4.5 ГБ; Gemma E2B — суттєво легша (користувач натренував власну LoRA на E2B саме заради економії)
- Whisper small int8 ≈ 250-400 МБ (не вантажиться взагалі при `text_mode: true`)
- StyleTTS2 UA (`tts.engine="pytorch"`) ≈ 700 МБ-1 ГБ
- StyleTTS2 UA (`tts.engine="onnx"`) — ~1 ГБ менше за pytorch-рушій
- **mBART verbalizer** (якщо `use_verbalizer: true`) ≈ 1.2-2.4 ГБ — **тримай вимкненим** (`false`). `num2words` покриває практично всі побутові числа без цієї важкої моделі.

**Витік пам'яті при повторній ініціалізації `TTSHandler` в одному процесі** — див. розділ "benchmark.py" вище. Стосується будь-якого коду (не лише `benchmark.py`), який створює кілька `TTSHandler` за життя одного процесу Python.

Перед тим як додавати нову модель — заміряй її RSS окремо, а не покладайся на документацію моделі.

## Відомі граблі (не наступай повторно)

1. **`re.search()` для пошуку "першого достатньо довгого речення" в `generate_response`** — якщо шукати найпростішим `re.search`, він завжди повертає найперший збіг пунктуації і "застряє", якщо те речення коротше за поріг. Треба перебирати `re.finditer` і брати перший, що задовольняє довжину.

2. **Подвійна нарізка тексту.** LLM (`llm_handler.py`) і TTS (`tts_handler.py`) обидва мають логіку нарізки на шматки. Якщо LLM віддає короткі шматки, а TTS ще й ріже їх додатково — кожен шматок платить фіксований оверхед виклику StyleTTS2 (~4s) окремо. **Уточнення після редизайну `_split_to_parts`:** тепер TTS свідомо НЕ мерджить кілька завершених речень в один виклик (раніше мердж до 240 симв. змушував чекати весь блок одним 9+-секундним викликом) — кожне речення йде окремим викликом заради швидшого першого звуку. Це збільшує кількість викликів навмисно; не "оптимізуй" це назад до мерджу, не порадившись — компроміс свідомий (менша сумарна пропускна здатність заради нижчої затримки до першого звуку).

3. **Кодування mp3 всередині гарячої фази.** Ніколи не роби `AudioSegment.from_mp3()` + конкатенація + `export()` на кожному шматку тексту під час активного TTS-рендеру. Накопичуй сирі wav-чанки в `_session_wavs` і кодуй **один раз** у `flush_session_audio()` після того, як репліка повністю відзвучала.

4. **`KMP_DUPLICATE_LIB_OK=TRUE`** на початку `main.py` — це маскування конфлікту версій OpenMP-рантайму, а не лікування. Якщо з'являється нестабільність/Access Violation під навантаженням кількох потоків — підозрюй цей прапорець.

5. **Незавершені git-merge конфлікти.** Перед будь-яким комітом після merge/rebase:
   ```powershell
   Select-String -Path *.py -Pattern "^<<<<<<<|^=======|^>>>>>>>"
   python -m py_compile main.py llm_handler.py tts_handler.py audio_handler.py extract_preset.py benchmark.py
   ```
   Обидві команди мають повернути порожній вивід/без помилок.

6. **`n_threads` без `n_threads_batch` у `Llama(...)`.** Якщо хтось прибере `n_threads_batch` з виклику конструктора — prefill почне ділити той самий малий бюджет потоків, що й decode, і "Пошук думки" в логах різко зросте (спостережено: 8.29s замість 1.5-2.5s).

7. **Змішування мов при слабшій LLM.** Менші квантування/моделі частіше вставляють російські слова в україномовну відповідь, особливо в саркастичному тоні. `_looks_ukrainian()` (п.15 нижче) частково захищає від найгірших випадків (повний зрив в іншу мову), але НЕ фільтрує окремі вкраплення чужомовних слів у переважно українському реченні — той текст все одно летить у StyleTTS2 UA, навчену лише на українській фонетиці. Якщо змінюєш модель на легшу — обов'язково перевір кілька реплік на предмет мовного змішування.

8. **Whisper-галюцинації на короткому/нечіткому старті запису.** "Привіт" → "Дивіт", "Цікавим" → "Мисикавим". `hallucination_blacklist` у `audio_handler.py` ловить лише повністю вигадані фрази-привиди, не спотворення реальних слів. Для справжнього обрізання країв (не галюцинацій) — див. розділ "Мікрофон" вище (`pre_roll_ms`/`vad_speech_pad_ms`), це окрема причина з окремим фіксом.

9. **`tts.mode=2` (клонування голосу) з `tts.engine=onnx` — навмисна помилка, не баг.** `_prepare_voice()` кидає `ValueError` одразу при старті. Причина — `models/styletts2.onnx` експортований без voice-encoder'а. Не "фіксь" це підміною на мовчазний fallback у `pytorch`. Правильний шлях: `extract_preset.py` (клонування офлайн, один раз) → `.pt`-пресет → `mode=1` + `engine=onnx`.

10. **`torch.set_num_interop_threads()` — лише один раз за процес.** Див. розділ "Бюджет потоків" вище. Не прибирай `try/except RuntimeError` навколо цього виклику в `tts_handler.py`.

11. **Daemon-потоки `TTSHandler` тримають `self` живим вічно без явного `shutdown()`.** `_text_processing_worker`/`_audio_playback_worker` — нескінченні `while True` на bound-методах; `del tts_module` сам по собі нічого не звільняє, поки потік не отримає сигнал зупинки. Критично для будь-якого коду, що створює кілька `TTSHandler` в одному процесі (див. "benchmark.py" вище). У `main.py` (один `TTSHandler` на весь процес) це не проблема — не додавай виклик `shutdown()` туди без причини, він там не потрібен.

12. **`llama_log_callback` і збирач сміття.** `llama.cpp` логує через C-колбек (`llama_log_set`). Без сильного посилання на цей колбек на рівні МОДУЛЯ (не локальна змінна в `__init__`) Python GC прибирає функцію-колбек ще до того, як бібліотека встигає нею скористатись — звідси `Exception ignored on calling ctypes callback function`. Фікс (мовчазний колбек + `_LLAMA_LOG_CALLBACK` на рівні модуля) уже в `llm_handler.py` — не переноси цю реєстрацію всередину класу чи функції.

13. **Тире/двокрапка/крапка з комою — НЕ кінці речення для TTS-нарізки.** `_split_to_parts` колись ловив `—–;:` у тому самому регексі, що й `.!?` — речення типу "Чотири — це вже не так просто" розривалось прямо на тире як на дві "сентенції", даючи чутний ефект заїкання/обрубаних фраз. Зараз первинний спліт ловить ЛИШЕ `.!?…`; тире/двокрапка/крапка з комою йдуть у `_split_long_sentence` (вторинна нарізка лише для ЗАДОВГИХ речень). Не повертай їх у первинний регекс.

14. **`parallel_chunks > 1` ламає звук.** Див. окремий розділ вище — це достатньо серйозно для власного розділу, не лише пункту списку.

15. **LLM іноді зривається в неукраїнський "потік свідомості" замість відповіді** (спостережено: модель почала вголос критикувати свою попередню відповідь англійською — `"(Self-correction applied... I will simplify this structure.)"`). `_looks_ukrainian()` у `llm_handler.py` — груба перевірка частки кириличних літер (поріг 50%) перед кожним `yield`; якщо сегмент не проходить — генерація негайно обривається (`break`, не просто пропуск), сміття не йде в TTS і не потрапляє в історію діалогу. Це пластир на симптом, не лікування причини (поведінка конкретного файнтюну) — якщо зривається часто, а не раз на кілька годин, розглянь зниження `temperature` або іншу модель.

## Незавершені експерименти / відкриті питання

- **`diffusion_steps`** у `tts_handler.py` (`self.multi_model.model.diffusion_steps`) — теоретично мало б лінійно впливати на швидкість синтезу, але тест (steps=3→1) не показав очікуваного прискорення. Стосується лише `engine="pytorch"` — в ONNX-графі кроки дифузії зашиті на етапі експорту, з коду їх не поміняти.
- ~~Паралельний синтез шматків (`parallel_chunks`)~~ — **ЗАКРИТО, відхилено.** Підтверджено ламає звук на обох рушіях (див. окремий розділ вище). Не повертайся до цього без верифікованого фіксу потокобезпеки препроцесингу.
- ~~`llm.n_threads=4` + `tts.n_threads=4`~~ — **протестовано, без виграшу** порівняно з `llm=3`. Приріст зупиняється на `llm.n_threads=3`.
- Динамічне перемикання `torch.set_num_threads()` між фазами (менше під час LLM-генерації, більше після) обговорювалось, але не реалізовано.
- Розпаралелення головного циклу між STT/LLM/TTS — див. попередження в розділі "Архітектура" вище.

## Перевірка перед комітом

Мінімальний чек-лист для будь-якої зміни в `*.py` чи `config.json`:

```powershell
python -m py_compile main.py llm_handler.py tts_handler.py audio_handler.py extract_preset.py benchmark.py
python .\main.py
```

Якщо зміна стосувалась `tts_handler.py` — прожени `main.py` **з обома значеннями `tts.engine`**, а не лише з тим, яке зараз стоїть у `config.json`.

Скажи щось голосом (або текстом у `text_mode`), дочекайся 2-3 реплік, переконайся що:
- нема traceback/винятків у консоль
- `output.mp3` записується один раз наприкінці репліки, а не по кожному шматку
- перше речення озвучується окремо й швидко, а не разом з усім монологом
- звіт по кожній фразі друкується ЖИВЦЕМ (одночасно зі звуком), а не одним блоком постфактум

Якщо зміна стосувалась продуктивності (потоки, рушій, `parallel_chunks`) — прожени `python .\benchmark.py` замість одиничного ручного тесту, порівняй з попередніми числами з CSV. Регресія на 20%+ без пояснення означає, що щось зламано.

## Стиль коду в цьому проєкті

- Логування — через `from logger_config import log` (`log.info/warning/error/critical`), не голий `print()` у нових модулях.
- Українські коментарі й лог-повідомлення з емодзі-префіксами (🎙️🧠📥✅❌🔥💾🧬) — усталений стиль проєкту.
- Конфігурація — все, що може мінятись між запусками, йде в `config.json`, а не хардкодиться в коді. Новий параметр — завжди `.get('key', default)` з розумним дефолтом.
- Перемикач "фіча-з-важким-ресурсом / без" — патерн `use_X: true/false` поруч зі шляхом до ресурсу (`X_path`), а не видалення/повернення шляху вручну. Уже так зроблено для `tts.use_verbalizer` і `llm.use_lora` — дотримуйся цього для майбутніх опційних важких залежностей.
