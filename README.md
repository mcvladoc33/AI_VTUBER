# 🎙️ Локальний Голосовий Помічник (AI VTuber)

Проєкт локальної цифрової асистентки з інтелектуальною активацією на голос (**VAD**), розпізнаванням мовлення (**STT**), локальним штучним інтелектом (**LLM**, опційно з власною LoRA) та реалістичним синтезом українського голосу (**TTS**).

Головний цикл (`main.py`) — **послідовний**: записати → розпізнати → згенерувати відповідь → озвучити → дочекатись завершення → повторити. Це свідомий вибір під слабке залізо без GPU: просто, передбачувано, без гонок за ядра між STT/LLM/TTS. Паралелізм є лише всередині TTS-модуля (два допоміжні потоки на синтез і відтворення) — це не три незалежні наскрізні конвеєри, а одна точкова оптимізація, щоб перше речення озвучувалось, не чекаючи, доки синтезується весь монолог.

---

## 💻 Системні вимоги
* **Процесор (CPU):** Intel(R) Core(TM) i5-8265U @ 1.60GHz (4 ядра / 8 потоків).
  * Дефолтний розподіл потоків: `llm.n_threads_batch=4` для важкого прорахунку промту (prefill), `llm.n_threads=2-3` для генерації токенів та `tts.n_threads=3` для рендеру звуку (PyTorch або ONNX Runtime — див. розділ TTS-рушії). Ці значення вивірені через `benchmark.py` на реальних замірах, не інтуїтивно.
* **Оперативна пам'ять (RAM):** 12,0 ГБ (загальне споживання разом із моделями — ~7-8 ГБ на PyTorch-рушії TTS, ~1 ГБ менше на ONNX-рушії; STT (Whisper) не вантажиться взагалі в текстовому режимі).
* **Відеокарта (GPU):** Інтегрована Intel UHD Graphics 620 (всі обчислення переведені на CPU).

## ⚙️ Налаштування та запуск

### 1. Створення віртуального оточення та встановлення залежностей

Проєкт розроблено та оптимізовано під **Python 3.11**. Відкрийте термінал у корені папки проєкту та виконайте:

```bash
# 1. Перевірте версію Python (має бути 3.11.x)
python --version

# 2. Створіть чисте віртуальне оточення .venv
python -m venv .venv

# 3. Активуйте створене віртуальне оточення
# Для PowerShell:
.\.venv\Scripts\Activate.ps1
# Для звичайного CMD:
.\.venv\Scripts\activate.bat

# 4. Оновіть pip
python -m pip install --upgrade pip

# 5. Встановіть бібліотеки
pip install -r requirements.txt
```

### 2. Завантаження ШІ-моделей

1. Покладіть GGUF-файл моделі мислення (і, за бажанням, LoRA-адаптер) у папку `models/`.
2. Запустіть скрипт для автоматичного скачування ваг українського голосу StyleTTS2 та лінгвістичного вербалізатора чисел mBART:

```bash
python download_models.py
```

### 3. Налаштування FFmpeg

Переконайтеся, що у корені проєкту є папка `bin/`, де лежать `ffmpeg.exe` та `ffprobe.exe`. Модуль `tts_handler.py` автоматично додає їх до системного шляху (PATH) під час старту.

### 4. Запуск помічниці

```bash
python main.py
```

## 🛠️ Як це працює

`main.py` — простий `while True`: кожен хід розмови виконується **по черзі**, а не як три постійно живі паралельні конвеєри:

```text
записати мікрофон → STT (Whisper) → LLM (Gemma, стрімом) → TTS (озвучити) → дочекатись кінця відтворення → повторити
```

Наступний запис мікрофона не почнеться, доки повністю не договорить попередня репліка. Це навмисно просто — на 4-ядерному CPU без GPU постійні фонові STT/LLM/TTS-потоки давали нестабільність і не окупались приростом швидкості.

1. **STT:** мікрофон пишеться через VAD (RMS-поріг), із кільцевим pre-roll буфером (`mic.pre_roll_ms`), що ловить м'який початок слова ще до спрацювання порогу. Whisper (`int8`) транскрайбить аудіо з додатковим VAD-паддінгом (`stt.vad_speech_pad_ms`) проти обрізання країв фрази вже під час розпізнавання.
2. **LLM:** отримує текст, генерує відповідь **стрімом**, ще під час генерації ріже готові речення й одразу передає їх у TTS — не чекаючи, доки згенерується вся відповідь цілком. Опційно працює через власний LoRA-адаптер (`llm.lora_path`/`llm.use_lora`).
3. **TTS:** `TTSHandler` тримає всередині себе два допоміжні daemon-потоки — синтез і відтворення. Поки перший синтезований шматок вже грає у колонках, наступний вже може синтезуватись, і синтез перших речень перекривається в часі з тим, як LLM ще дописує решту відповіді.

Під час відтворення кожна фраза друкується в консоль **живцем**, у момент, коли вона реально звучить:

```
🤖 Селті:
 ➔ Привіт. Я чудово.  [4.26s = 1.49с (думка) + 2.77с (синтез)]
      ...тиша 1.80s...
 ➔ Ти як?  [6.85s = 4.34с (думка) + 2.51с (синтез)]
      ...тиша 0.33s...
 ➔ Бачу ти теж не надто поганий сьогодні.  [3.94s = 3.94с (синтез)]
  📊 LLM 5.83s | TTS 9.22s | тиша 2.13s | всього 13.06s
```

Число в дужках — скільки часу зайняло саме на цю фразу (LLM-час рахується лише на першому шматку кожного сегмента, щоб не дублюватись, якщо сегмент розрізало на кілька TTS-викликів). `...тиша...` — реальна пауза між озвучуванням сусідніх фраз, яку фактично чує користувач.

**Команди голосового переривання ("Стоп!") в поточній архітектурі немає** — вона існувала в попередній, черговій версії проєкту, від якої свідомо відмовились через нестабільність на цьому залізі.

## ⚡ TTS-рушії: PyTorch vs ONNX Runtime

`tts_handler.py` вміє синтезувати голос двома способами — через звичайний PyTorch-інференс `StyleTTS2` або через `onnxruntime`, якщо в `models/` лежить експортований `styletts2.onnx`. Перемикання — одним полем у `config.json`:

```json
"tts": {
  "engine": "onnx",
  "onnx_model_path": "models/styletts2.onnx"
}
```

**Виміряно на цьому залізі** (i5-8265U, `tts.n_threads=3`, той самий пресет, ідентичні репліки):

| Метрика | `engine: pytorch` | `engine: onnx` | Різниця |
|---|---|---|---|
| Синтез шматка ~33 симв. | 3.98s | 3.02s | ~24% швидше |
| Синтез шматка ~68 симв. | 6.08s | 4.23s | ~30% швидше |
| RAM у стані спокою | 10.5G / 11.8G | 9.43G / 11.8G | ~1 ГБ менше |
| Сумарний час типової репліки (`benchmark.py`, однакові потоки) | 22.35s | 20.41s | ~9% швидше |

ONNX виграє за швидкістю й пам'яттю. Водночас **суб'єктивно PyTorch звучить приємніше** на слух — це неможливо перевірити об'єктивно (внутрішні параметри готового `.onnx`-файлу, зокрема кроки дифузії, зашиті на етапі експорту й недоступні з коду). Якщо `tts.mode=1` (не потрібне клонування голосу) — вибір рушія залишається на ваш розсуд: швидкість+пам'ять проти суб'єктивної якості голосу.

**Обмеження ONNX-рушія:** експортований граф приймає лише готовий вектор стилю (`s_prev`) — у ньому немає voice-encoder'а. Тому **динамічне клонування голосу (`tts.mode=2`) з `engine=onnx` не підтримується** — `TTSHandler` одразу кине зрозумілу помилку при старті. Для `mode=1` (готовий `.pt`-пресет) різниці між рушіями по функціоналу немає.

**Як отримати клонований голос і при цьому лишитись на швидкому ONNX:** клонування виноситься в окремий одноразовий офлайн-крок через `extract_preset.py`:

```bash
python extract_preset.py --audio sample.wav
python extract_preset.py --audio references/sample.wav
python extract_preset.py --audio references/sample.wav --name "Мій голос"
```

Скрипт вантажить повну PyTorch-модель `StyleTTS2` лише один раз, викликає `model.extract_voice_features(audio_path)` для референс-аудіо з `references/` і зберігає результат як `<назва>.pt` у `voices/` (за замовчуванням — ім'я самого аудіофайлу). Після цього просто вказуєш новий файл у `tts.preset_filename`, ставиш `tts.mode: "1"` і `tts.engine: "onnx"` — і отримуєш кастомний голос на швидкому рушії.

**Важливо:** не вмикайте `tts.parallel_chunks > 1` — підтверджено спричиняє чутне пошкодження звуку (заїкання на початку слів) на обох рушіях. Значення `1` — навмисний дефолт, не оптимізація, яку "забули" ввімкнути.

## 🧬 LoRA-адаптери для LLM

Якщо ви натренували власний LoRA-адаптер (наприклад, через `llama-cli.exe --lora`), його можна підключити без злиття з базовою моделлю:

```json
"llm": {
  "model_path": "models/base-model.gguf",
  "lora_path": "models/adapter-lora.gguf",
  "use_lora": true,
  "lora_scale": 1.0
}
```

`use_lora` дозволяє швидко порівнювати модель "з LoRA" і "без", не видаляючи сам шлях з конфігу. Якщо LoRA натренована разом з персонажем — перевірте, чи не конфліктує вона з `character.system_prompt` (LoRA могла вже "запам'ятати" стиль спілкування самостійно).

Потрібна відносно свіжа версія `llama-cpp-python` (GGUF-формат LoRA підтримується не в усіх версіях) — якщо при старті виникає `TypeError` про невідомий аргумент `lora_path`, оновіть пакет: `pip install --upgrade llama-cpp-python`.

## 🧪 benchmark.py — автотестування конфігурацій

Замість ручного порівняння конфігурацій (потоки, рушій TTS) через перезапуски `main.py` — автоматизований прогін однієї фіксованої фрази через список варіантів:

```bash
python benchmark.py                              # дефолтний набір варіантів, 3 повтори кожен
python benchmark.py --reps 5                      # більше повторів — стабільніше середнє
python benchmark.py --phrase "Твоя фраза тут"
python benchmark.py --seed 0                       # вимкнути фіксацію seed (звичайна випадковість LLM)
python benchmark.py --mute                         # без реального відтворення звуку (швидше, менш точна "тиша")
```

На виході — порівняльна таблиця в консолі (LLM/TTS/тиша/всього по кожному варіанту) і CSV-файл з деталями кожного окремого прогону. Список варіантів для порівняння редагується у змінній `VARIANTS` на початку файлу — додавайте нові комбінації `n_threads`/`engine`/`parallel_chunks` туди.

### STT та мікрофон

* `stt.vad_min_silence_ms` / `stt.vad_speech_pad_ms` — власний VAD Whisper (Silero); `vad_speech_pad_ms` додає запас з обох боків знайденого сегмента мовлення проти обрізання країв слова вже на етапі розпізнавання.
* `mic.threshold` — поріг гучності (RMS) для детекції початку мовлення.
* `mic.silence_duration` — скільки секунд тиші після мовлення чекати перед зупинкою запису.
* `mic.pre_roll_ms` — скільки мс "передісторії" підхоплювати з кільцевого буфера, коли гучність щойно перевищила поріг (проти ковтання перших звуків слова).

### LLM та LoRA

* `llm.n_threads` / `llm.n_threads_batch` — потоки для генерації/обробки запиту відповідно. Дефолт `2`/`4`, підтверджено `benchmark.py` (підняття до `3` дає незначний виграш у межах шуму, до `4` — виграшу немає).
* `llm.lora_path` / `llm.use_lora` / `llm.lora_scale` — опційний LoRA-адаптер, див. розділ вище.

### TTS

* `tts.engine`: `"pytorch"` (підтримує клонування голосу `mode=2`, суб'єктивно приємніший голос) або `"onnx"` (швидше й економніше по RAM, лише готові `.pt`-пресети `mode=1`).
* `tts.onnx_model_path`: шлях до `.onnx`-файлу. Використовується лише коли `tts.engine="onnx"`.
* `tts.max_chunk_chars`: максимальна довжина ОДНОГО шматка для одного виклику синтезу; довші речення ріжуться по комах/тире (не по словах, якщо можливо — звучить природніше).
* `tts.parallel_chunks`: **тримай `1`**. Значення `> 1` підтверджено ламає звук — див. розділ "TTS-рушії" вище.
* `tts.n_threads`: потоки, виділені TTS-рушію (діє однаково на PyTorch і ONNX).

**Правило балансу потоків:** сума `llm.n_threads + tts.n_threads` не повинна суттєво перевищувати кількість фізичних ядер (`4` на цьому залізі) — LLM і TTS реально перекриваються в часі навіть у послідовній архітектурі головного циклу, тож повне навантаження обох одночасно цілком реальне, не лише теоретичне.

## 🔗 Використані ШІ-технології та Джерела

* **[IPA UK](https://github.com/patriotyk/ipa-uk)** — фонетичний конвертер тексту в IPA.
* **[SoundDevice](https://python-sounddevice.readthedocs.io/)** — низькорівнева робота з аудіопотоками Windows.
